# Validated Intent

We want to **create a single Pacco Login UI used by both Admin and normal users, followed by a role-aware welcome landing page**,
to achieve **a simple, consistent role-aware login experience that gives Pacco its first browser entry point without introducing business functionality**,
measured by:
-- valid credentials authenticate through the existing identity-service and land the user on the landing page, where an Admin sees “Welcome to Admin Area” and a normal user sees “Welcome”
-- invalid credentials produce a single clear, non-disclosing error and leave the login form usable
-- required-field validation appears on empty submit, the Login button shows a processing state, and duplicate submissions are blocked while a request is in flight
-- an unauthenticated visitor to the landing page is returned to Login by the client-side route guard, an expired token returns the user to Login with a session-expired message, and logout returns the user to Login
-- no dashboard widget or post-landing business functionality ships with this feature,
within **a net-new Pacco browser login surface comprising the login screen, the role-aware landing page, client-held session handling and logout, anchored on CAP-01 Identity & Access Management for credentials and on CAP-02 Edge Routing & Access Enforcement for reachability — explicitly excluding separate Admin and normal-user login screens, registration, password recovery, role management, post-landing business functionality, and changes to the Pacco authentication or authorization backend, with the sole permitted edge change being the addition of the UI origin to the gateway CORS allowed-origins list (no new edge routes)**,
under constraints of **the existing Pacco authentication and role model: one common login screen with no user-selected role; user type resolved only from the authenticated identity's role claim, never from username or email; unknown or unsupported roles never resolving to Admin; passwords never logged or displayed; no credentials hard-coded in the frontend; no duplicate submissions while a request is in progress; no raw backend exceptions or stack traces shown to users; logout enforceable only as a client-side discard; and a deliberately minimal landing page**.

## Assumptions

- ASM-1: Authentication uses the existing identity-service sign-in route reached through the Ntrada edge as `/identity/sign-in`; sign-in and sign-up are the platform's only explicitly unauthenticated edge routes, so this feature introduces no new unauthenticated surface.
- ASM-2: “Admin” means the token's `role` claim carrying the value `admin`. The platform compares that value case-insensitively in `IdentityContext.IsAdmin` while the edge claim gate uses exact-string equality, so the UI treats `admin` case-insensitively and resolves every other value — including an absent claim — to the normal-user experience (see NFR-5).
- ASM-3: Sign-in failure copy is a single generic message covering both an unknown email and a wrong password, because CAP-01 Identity & Access Management returns the same failure for both and the UI must not narrow it (see NFR-4).
- ASM-4: The landing page is a single client-side route whose only content is the role-aware welcome message; it fetches nothing from domain services, consistent with the stated guardrail that it remain intentionally simple.
- ASM-5: The delivery surface is desktop and mobile **web browsers** only; no native or packaged mobile client is in scope.
- ASM-6 **(decision — resolved clarification)**: “No changes to the authentication or authorization backend” permits exactly one edge configuration change: naming the UI origin in the gateway CORS allowed-origins list. No new route is added to `ntrada.yml`, and no identity-service or authorization code changes. That configuration change takes effect only on a gateway process restart (see NFR-19).
- ASM-7 **(decision — resolved clarification)**: Logout is a client-side discard of the held token only; the UI never claims server-side session termination. An expired token returns the user to Login with a session-expired message (see NFR-7).
- ASM-8 **(decision — resolved clarification)**: Landing-page protection is a client-side route guard that reads the role claim from the locally held token. There is no server round-trip on protected-route entry and no `GET /identity/me` call. The guard is a usability affordance, not an access-control boundary (see NFR-8).
- ASM-9: Because the landing page issues no backend calls, session expiry is detected client-side from the token's `exp` value rather than by reacting to a 401 — there is no call from which a 401 could arrive.
- ASM-10: The bearer token is never placed in a URL, log line, analytics event or error report (see NFR-10).
- ASM-11: The login screen and landing page meet WCAG 2.1 AA (labelled inputs, programmatically associated error text, keyboard operability, visible focus). No accessibility standard is catalogued for the platform and the only quality gate is a build that a failing test suite does not break, so an industry default is assumed for an authenticated entry point (see NFR-14).
- ASM-12: Failed sign-in attempts are traceable through the platform correlation identifier when the edge sets it; the gateway declares `Request-ID`, `Resource-ID`, `Trace-ID` and `Total-Count` as CORS-exposed headers, but a recorded gap notes the header is never set by any code in the workspace, so the UI captures it opportunistically and must not depend on it (see NFR-15).
- ASM-13: The gateway base URL is supplied to the UI as per-environment configuration, never compiled into the shipped asset — the existing browser asset's hard-coded absolute backend URL is treated as an anti-pattern not to repeat (see NFR-17).
- ASM-14: The login surface ships with its own build, artifact, version and pipeline stage rather than inheriting the existing diagnostic page's coupling, where UI availability is tied to operations-service availability and any frontend change forces an operations-service rebuild and redeploy (see NFR-20). Which deployable hosts it is OQ-1.
- ASM-15 **(decision — resolved clarification)**: The access token is held in `sessionStorage` — the session survives a page refresh and ends when the tab closes. No cookie and no server-side session are introduced, consistent with the platform rule that no route uses a session cookie, session id or server-side session and that identity-service is not a session store. This is also the platform's first client-side persistence, since today no localStorage or sessionStorage crosses any hand-off; that novelty is deliberate and bounded to the token (see NFR-22).
- ASM-16: The UI applies its own client-side timeout to the sign-in request and bounds the Login processing state, because no total request timeout is configured anywhere at the edge and the gateway HTTP retry policy can add several seconds on top of the downstream's own timeouts (see NFR-21).
- ASM-17: The login surface establishes its own frontend toolchain baseline (build, lint/format, dependency manifest) because the platform's only existing browser asset was authored and shipped without Node tooling and no contributing guide, scaffold, template or architecture test exists in any of the fourteen clones to inherit (see NFR-23).

## Open Questions

- OQ-1 [Architecture]: Where does this UI ship and how is it built and released? `Pacco.Web` is an empty solution aggregator with no deployable runtime, the client decision for it is recorded as an open catalog item, and the platform's only browser asset is a static page inside the operations-service image. Options: (a) new standalone web deployable with its own pipeline, (b) static assets served from an existing service image, (c) same-origin assets served by the gateway. Suggested: new standalone deployable *(suggested — owner decides)*; note option (c) sits in tension with the stated scope, which assumes a cross-origin UI and names the CORS allowed-origins entry as the sole edge change. Due before Architecture Validation completes.
- OQ-2 [Security / Architecture]: Which concrete origin or origins replace the CORS wildcard, per environment? The catalog carries “Whose origin should replace the CORS wildcard for Pacco.Web?” as an unresolved item, and the current `allowedOrigins: ['*']` with `allowCredentials: true` is forbidden by the CORS specification. Recommended default: one explicit origin per environment (local, docker, production), derived from OQ-1's hosting answer, with no wildcard in any environment. Due at the gateway configuration change.
- OQ-3 [Product]: What does a user whose token carries **no** `role` claim at all see — as distinct from one carrying an unrecognised role value? Recommended default: treat both identically as a normal user and show “Welcome”, never Admin, which is the safe reading of the stated guardrail and needs no new backend behaviour.
- OQ-4 [QA]: What automated coverage is expected for this feature? The platform's Test Gate is vacuous — the build is not broken by a failing test suite, the suite is not run in CI, and the CI badge is recorded as false confidence — so there is no house standard to inherit. Recommended default: unit and component tests for the login form, validation, processing state and route guard, plus one happy-path end-to-end run per role. Due at spec sign-off.

## Non-Functional Requirements

- NFR-1 [security]: Password values are never logged, displayed, or persisted by the UI — target: zero occurrences in logs, DOM, or client storage (source: requirements_doc, confidence: high)
- NFR-2 [security]: No credentials or secrets are hard-coded in the frontend bundle — target: zero hard-coded credentials (source: requirements_doc, confidence: high)
- NFR-3 [security]: Raw backend exceptions or stack traces are never rendered to the user — target: zero raw exception surfaces (source: requirements_doc, confidence: high)
- NFR-4 [security]: Sign-in failure messaging must not distinguish an unknown email from a wrong password — target: one generic failure message for every invalid-credential outcome (source: cake:security, confidence: high)
- NFR-5 [security]: Admin determination binds solely to the token `role` claim value `admin`, with no email or username inference, no role hierarchy and no “any of” semantics; unrecognised or absent roles resolve to normal user — target: 100% of role decisions derived from the token claim (source: cake:security, confidence: high)
- NFR-6 [security]: The authenticated session ends at the access token's absolute lifetime, and no refresh-token endpoint is routable through the edge — target: 60 minutes (source: cake:security, confidence: high)
- NFR-7 [security]: Logout must not claim server-side session termination — a revoked access token is still accepted by the gateway and all eight domain services until it expires, because revocation is consulted only by the issuing service — target: client-side discard is the only enforceable logout (source: cake:security, confidence: high)
- NFR-8 [security]: The client-side route guard is a usability affordance, not an access control — the authentication boundary sits at the edge with fail-open in-service authorization, so no data beyond what the held token already carries may be gated client-side — target: zero security decisions delegated to the browser (source: cake:security, confidence: high)
- NFR-9 [security]: The UI's origin must be named explicitly in the edge CORS allowed-origins list; the current `allowedOrigins: ['*']` combined with `allowCredentials: true` is forbidden by the CORS specification and either allows any origin with credentials or silently fails credentialed cross-origin calls — target: explicit origin list, no wildcard (source: cake:security, confidence: high)
- NFR-10 [privacy_compliance]: The bearer token is never written to a URL, log line, analytics event or error report — target: zero token occurrences outside the chosen client store and the Authorization header (source: assumption, confidence: medium)
- NFR-11 [concurrency]: Duplicate login submissions are prevented while a request is in flight — target: at most one in-flight sign-in request per session (source: requirements_doc, confidence: high)
- NFR-12 [reliability_resilience]: Authentication or identity-service failures leave the UI recoverable — the processing state clears and the form remains usable — target: 100% of failure paths return to a usable form (source: requirements_doc, confidence: high)
- NFR-13 [usability_accessibility]: Required-field validation, the Login processing state, and failure messaging are each clearly presented on the login screen — target: all three states visibly rendered (source: requirements_doc, confidence: high)
- NFR-14 [usability_accessibility]: The login screen and landing page conform to WCAG 2.1 AA — target: WCAG 2.1 AA (source: assumption, confidence: medium)
- NFR-15 [observability]: Failed sign-in attempts are traceable through the platform correlation identifier without exposing backend detail, and the UI must degrade cleanly when the header is absent — target: a correlation Request-ID captured for every failed sign-in where the edge emits one (source: cake:observability, confidence: medium)
- NFR-16 [portability_infra]: Every UI-to-backend call traverses the Ntrada edge allow-list; a route not declared in the active manifest is unreachable and direct service access bypasses the edge claim gates — target: zero direct-to-service calls from the browser (source: cake:architecture, confidence: high)
- NFR-17 [portability_infra]: The gateway base URL must be environment-configurable rather than a hard-coded absolute URL in the shipped asset — target: zero hard-coded backend URLs; one configuration value per environment (source: cake:architecture, confidence: high)
- NFR-18 [portability_infra]: Every HTTP method the UI issues cross-origin must appear in the edge CORS method allow-list, which today declares only `post`, `put` and `delete` — target: method allow-list covers 100% of the UI's cross-origin verbs (source: cake:architecture, confidence: high)
- NFR-19 [operational_readiness]: The CORS allowed-origins change takes effect only on a gateway process restart, since no code path modifies routes and configuration is not hot-reloaded — target: the origin change is scheduled as a gateway restart, not a live edit (source: cake:operations, confidence: high)
- NFR-20 [operational_readiness]: The login surface ships with its own build, artifact, version and pipeline stage rather than binding its availability to a domain service's process — target: an independently deployable UI boundary (source: cake:architecture, confidence: medium)
- NFR-21 [performance]: The sign-in call must be bounded client-side, because no total request timeout is configured anywhere at the edge and the gateway HTTP retry policy can add up to 6 seconds on top of the downstream's own timeouts — target: an explicit client-side request timeout, with the Login processing state clearing and the form returning to a usable state at that bound (source: cake:architecture, confidence: high)
- NFR-22 [security]: The access token is held in `sessionStorage` — surviving a refresh, discarded when the tab closes — and never in a cookie, a session id or any server-side session, none of which exist on any Pacco route — target: exactly one client-side token store, scoped to the tab, with no cookie set by the UI (source: requirements_doc, confidence: high)
- NFR-23 [maintainability]: The login surface carries its own documented frontend toolchain (dependency manifest, build, lint/format) rather than repeating the existing browser asset's no-Node-tooling authoring model — target: a committed frontend build and lint baseline shipped with the surface (source: assumption, confidence: medium)

identity's role claim — the value admin compared case-insensitively showing "Welcome to Admin Area" and every unrecognised or absent value showing "Welcome", never inferred from username or email and ## 2. Pacco Session Continuity, Landing-Page Guard & Logout

We want an authenticated user's held session to survive a page refresh and end when the browser tab closes, held in exactly one tab-scoped client store with no cookie set by the UI, no session id and no server-side session; an unauthenticated visitor navigating to the landing page to be returned to Login by the client-side route guard that reads the role claim from the locally held token with no server round-trip and no additional identity call on protected-route entry; a user whose access token has passed its absolute lifetime to be returned to Login with a clear session-expired message, detected client-side from the token's expiry because the landing page issues no backend call from which a failure could arrive; and a user choosing Logout to have the held token discarded and be returned to Login, with the UI never claiming server-side session termination because a revoked access token is still accepted by the gateway and the domain services until it expires — the guard being a usability affordance only, with no security decision delegated to the browser and no data gated client-side beyond what the held token already carries, so that the post-login experience is protected from unauthenticated entry and every session end returns the user cleanly to the login experience, measured by every unauthenticated, expired or post-logout landing-page entry returning the user to Login, validated when an unauthenticated visitor is redirected to Login, an expired token produces the session-expired message on Login, and Logout returns the user to Login, operationally verified by the session surviving a page refresh, ending when the tab closes, and the token being absent from the client store after logout, with the access token's absolute lifetime at 60 minutes.

- Metric: unauthenticated or expired landing-page entry returns the user to Login
- Target: 100% of unauthenticated / expired / post-logout landing entries return to Login; access-token absolute lifetime 60 minutes; exactly one tab-scoped client token store and zero cookies set by the UI
- Priority: 2

## 3. Pacco Browser Origin Enablement at the Ntrada Edge

We want a platform operator to make the Pacco login surface reachable from a browser by naming one explicit UI origin per environment in the gateway's declarative CORS allowed-origins configuration in place of the current wildcard, verifying that the CORS method allow-list covers every cross-origin verb the login surface issues, and scheduling the change as a gateway process restart because no code path modifies routes and gateway configuration is not hot-reloaded, while adding no new edge route, no new unauthenticated surface beyond the already-unauthenticated sign-in route, no backend-for-frontend, and no identity-service or authorization code change, so that the browser login surface can reach the platform's single north-south edge without weakening the edge's access enforcement, measured by an explicit per-environment origin list with no wildcard entry, validated when a credentialed cross-origin sign-in call from the named origin succeeds and a call from an unnamed origin is refused by the browser, operationally verified by the change taking effect after the scheduled gateway restart in each environment with every UI-to-backend call still traversing the edge allow-list. Resolution required before spec generation: the catalogued edge policy is allowedOrigins ['*'] combined with allowCredentials true — a combination the CORS specification forbids — and no concrete per-environment origin has been named because the hosting answer is still open (OQ-2, dependent on OQ-1); Product/Architecture decision required.

- Metric: explicit per-environment CORS origin with no wildcard
- Target: zero wildcard origins in any environment; CORS method allow-list covers 100% of the UI's cross-origin verbs; zero new edge routes; zero direct-to-service calls from the browser
- Priority: 1

## Questions and answers

### 1. Session persistence across refresh and tabs

**Question:** Must the signed-in session survive a browser refresh or a new tab, or should the user re-authenticate whenever the page reloads?

**Answer:** – sessionStorage — survives refresh, ends with the tab

## Additional user input

• Does “no changes to the existing Pacco authentication or authorization backend” also rule out edge/gateway configuration changes — naming the UI origin in CORS, or adding a route to ntrada.yml?Why this matters: Architecture and Security own this, and it decides execution viability: a browser client cannot call /identity/sign-in cross-origin unless its origin is named at the edge, and the identity token endpoints have no edge route today, so the answer determines whether this feature is buildable without touching the gateway configuration.
– CORS allowed-origin changes only — no new edge routes

• What must logout and session expiry actually do, given access tokens expire absolutely at 60 minutes and token revocation is not honoured at the gateway?Why this matters: Product and Security own the definition of “logged out”: revocation is honoured only by the issuing service, so a client-side discard is the only enforceable logout, and the answer sets the acceptance bar both for logout and for what happens when the token expires mid-session.

– Client-side discard only; an expired token redirects to Login with a session-expired message

• On entering the landing page, is the user's identity and role re-validated against the server, or read from the locally held token?Why this matters: Architecture and Security own this seam: ADR-006 places the authentication boundary at the edge and leaves service handlers open, so the answer decides whether “unauthenticated users cannot access the landing page” means a client-side route guard over a decoded claim or a server-validated call to GET /identity/me on every protected-route entry.

– Client-side route guard reading the role claim from the held token
