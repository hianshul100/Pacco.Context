# Delivery Outcomes

## 1. Common Pacco Login Experience (DO1)

We want both Admin and normal users to load one common Pacco login screen, enter Email/Username and Password, see required-field validation when either field is empty, submit the Login button which shows a processing state and prevents duplicate submissions while a request is in progress, be authenticated against the existing Pacco identity-service sign-in capability reached through the declarative api-gateway north-south edge (ADR-004; edge-enforced authentication per ADR-006), be redirected to the landing page on success, and see a clear non-technical error on invalid credentials or on identity-service failure, so that Pacco gains its first authenticated end-user entry point without a separate Admin screen and without ever asking the user to declare their user type, measured by authentication outcomes surfaced safely and exactly once per submission, validated when empty fields block submission with visible validation, valid credentials authenticate and redirect, invalid credentials show a clear error, and an identity-service failure leaves the screen usable rather than broken, operationally verified by the login screen loading and completing a full sign-in round trip against the running identity-service through the gateway with no password value logged or displayed, no credentials hard-coded in the frontend, and no raw backend exception or stack trace reaching the user. Catalog does not surface a Pacco frontend/client architecture decision or UI foundation - Pacco.Web is an empty single-commit repository, no frontend asset or design system exists platform-wide, the repository is absent from every deployment manifest and from all gateway route configurations, and the ADR corpus explicitly excludes the platform client/frontend strategy because no decision was made; the browser access path (including the gateway CORS posture) needs ADR / architect review before specification finalization.

- Metric: authentication outcomes surfaced safely and exactly once per submission
- Target: 0 raw backend exceptions or stack traces shown to users; 0 password values logged or displayed; 0 duplicate login submissions accepted while a request is in progress
- Priority: 1
- Dependencies: none
- Contract edges: produces-for DO2 — the authenticated session and identity role claim
- Complexity: high

## 2. Role-Aware Landing Page with Session Protection and Logout (DO2)

We want an authenticated user to be taken to an intentionally simple landing page that determines user type solely from the authenticated identity role - within identity-service's closed lower-cased role vocabulary of user and admin - never inferring Admin from username or email address and never defaulting an unknown or unsupported role to Admin, showing 'Welcome to Admin Area' for Admin users and 'Welcome' for normal users, to be blocked and redirected back to Login whenever the landing page is requested without an authenticated session, and to log out and be returned to the login experience, so that Pacco has a verifiable role-aware post-login experience with no dashboard widgets or business functionality introduced, measured by the landing message always matching the authenticated identity role and the post-login surface never being reachable unauthenticated, validated when an Admin sign-in shows 'Welcome to Admin Area', a normal-user sign-in shows 'Welcome', an unknown or unsupported role does not show the Admin message, a direct landing-page request without a session redirects to Login, and logout returns the user to Login, operationally verified by the role-aware message and the redirect behaving identically on reload and after logout against live identity-service tokens. Resolution required before spec generation: raw intent requires logout support while declaring changes to the existing Pacco authentication and authorization backend out of scope, but the identity-service token-revocation endpoints have no gateway route in either gateway configuration and the gateway does not consult the revocation deny-list (ADR-007 split JWT trust root), so a logout that actually invalidates the issued token cannot be delivered without an edge or auth-backend change; Product/Architecture decision required on whether logout is client-side session discard only or warrants exposing revocation at the edge.

- Metric: landing message matches the authenticated identity role
- Target: 0 unknown-role or normal users shown 'Welcome to Admin Area'; 0 unauthenticated requests reaching the landing page
- Priority: 2
- Dependencies: DO1
- Contract edges: consumes-from DO1 — the authenticated session and identity role claim
- Complexity: medium

## Additional user input

### 1. Pacco frontend and client architecture decision, including gateway CORS posture

**Question:** What is the Pacco frontend/client architecture and UI foundation for the login surface — where does it ship, how is it built and released, and what browser access path and gateway CORS posture (which concrete origins replace the current wildcard, per environment) does it use?

**Why this matters:** Architecture owns this and it gates DO1. The catalog records no client decision for Pacco.Web — the repository is an empty solution aggregator with no deployable runtime, absent from every deployment manifest and from all gateway route configurations — no frontend asset or design system exists platform-wide, and the ADR corpus explicitly excludes the platform client/frontend strategy because no decision was made. The catalogued edge policy is `allowedOrigins: ['*']` with `allowCredentials: true`, a combination the CORS specification forbids, so the browser access path cannot be specified until this is decided.

**Owner:** Architecture

**Due:** before specification finalization.

**Answer:** _pending_

### 2. Logout semantics and token revocation at the edge

**Question:** Is logout a client-side session discard only, or does it warrant exposing identity-service token revocation at the gateway edge?

**Why this matters:** Product and Architecture own this and it gates DO2. The raw intent requires logout support while declaring changes to the existing Pacco authentication and authorization backend out of scope, but the identity-service token-revocation endpoints have no gateway route in either gateway configuration and the gateway does not consult the revocation deny-list (ADR-007 split JWT trust root). A logout that actually invalidates the issued token therefore cannot be delivered without an edge or auth-backend change, and the answer sets the acceptance bar for logout.

**Owner:** Product / Architecture

**Due:** before spec generation.

**Answer:** _pending_
